## 1. The engineering problem

Every lesson in this phase ended with "compare with SciPy". That was verification: an independent code solving the same equations. Real engineering codes have no SciPy to compare with, and the aircraft or spacecraft they size gets certified on their output, so the question "is this number right?" needs a procedure. NASA-STD-7009 (`@nasa-std-7009b`), written after the Columbia accident board found that a debris-impact prediction had been trusted beyond its evidence, defines the terms: **verification** is the process of determining that a model implementation accurately represents the developer's conceptual description (the equations are solved correctly); **validation** is the process of determining the degree to which a model is an accurate representation of the real world from the perspective of its intended use (the right equations are solved); and the standard requires that the uncertainty of the result, the verification and validation evidence, and the limits of the model's applicability be *reported* with every result that supports a critical decision.

This lesson does the whole procedure on a problem small enough to see every step: a transient one-dimensional heat-conduction solver for a strip-heated aluminium rail, u_t = α u_xx − βu + q(x, t) with the ends held at ambient. Code verification first: the solver must reproduce solutions whose exact form is known, and the **method of manufactured solutions** (`@langtangen-fd-computing-exponential-decay` 3.1.5, `@langtangen-linge-fd-computing-pdes` 2.2.3) supplies as many as we like; its observed order of convergence must equal the formal order, and we check that it catches two bugs planted in the solver. Solution verification next: on the real problem, which has no exact solution, three grids and Richardson extrapolation estimate the converged answer and the **grid convergence index** gives the numerical uncertainty of the 100-cell result (`@nasa-nparc-cfd-vv-tutorial`). Validation last: the model is compared with thermocouple data — **synthetic** data in this lesson, generated with a physical term (convective loss) the model omits, so the comparison fails in the way real comparisons fail, and we learn what the failure looks like, how calibrating one parameter hides it, and what should be reported.

Success criteria, written first: Thomas solver backward error below 20 ε; constant and polynomial solutions reproduced to 10⁻¹¹ K; observed order 2.00 ± 0.05 on two exact solutions; both planted bugs detected by the order test; Richardson extrapolation of the heater temperature within 10⁻⁴ K of an 800-cell reference, and the GCI of the 100-cell grid bounding its actual error; the validation metric rejects the lossless model and accepts the true one with reduced χ² between 0.5 and 2.

## 2. Understand and derive

### 2.1 Three words with precise meanings

NASA-STD-7009 separates *code verification* (the software solves the discrete equations without bugs: exact solutions, order tests, backward error), *solution verification* (how far the discrete solution on the grid actually used is from the exact solution of the continuous equations: grid convergence, iterative convergence), and *validation* (comparison with referent data from the real world, with uncertainties on both sides). Its credibility assessment adds *input pedigree*, *results uncertainty*, *results robustness* and the qualifications of the people; the reporting requirement is that a result be accompanied by its uncertainty, the assumptions and the V&V evidence. Appendix C of the Systems Engineering Handbook (`@nasa-seh-rev2`) teaches how to write a requirement that can be verified: a single statement with a measurable criterion and a method. "The solver shall be accurate" is not one. "The solver shall exhibit an observed spatial order of 2.0 ± 0.1 on the manufactured solution of §2.4 over grids of 25 to 200 cells, verified by test" is, and it is exactly what a `pytest` test encodes. Every test in this lesson is a requirement in that form.

### 2.2 The scheme and its truncation error

On a grid x_i = iΔx, i = 0 … nx, with time step Δt, the **θ-method** with central differences reads

(u_i^{n+1} − u_iⁿ)/Δt = θ[α D₂u^{n+1} − βu^{n+1} + q^{n+1}]_i + (1 − θ)[α D₂uⁿ − βuⁿ + qⁿ]_i,   D₂u_i = (u_{i−1} − 2u_i + u_{i+1})/Δx²,   (1)

with θ = ½ Crank–Nicolson and θ = 1 backward Euler. Taylor-expand the exact solution about (x_i, t_{n+½}) (`P02.02`). The time difference equals u_t + (Δt²/24)u_ttt + …; the θ-average of a quantity at n and n + 1 equals its midpoint value plus (θ − ½)Δt ∂_t(·) + (Δt²/8)∂_tt(·) + …; and D₂u = u_xx + (Δx²/12)u_xxxx + …. The scheme's **truncation error** is therefore

τ = (θ − ½)Δt (αu_xx − βu + q)_t + O(Δt²) + (Δx²/12) α u_xxxx + O(Δx⁴):   (2)

**second order in Δx for every θ, second order in Δt only for θ = ½**. The scheme is unconditionally stable for θ ≥ ½ (`P03.11`), so the error of the solution is O(Δx²) + O(Δt^{p_t}) with p_t = 2 or 1. With Δt ∝ Δx, both terms shrink by 4 per halving for Crank–Nicolson and the *observed order* must be 2; for backward Euler the Δt term shrinks by 2 and dominates, so the observed order falls to 1. Formula (2) is what we test; it also predicts the planted bug of §2.5.

Each time step is a tridiagonal solve: interior rows have diagonal 1 + θ(2r + βΔt) with r = αΔt/Δx², off-diagonals −θr, right-hand side from the known level plus the boundary values at t_{n+1}. The **Thomas algorithm** is Gaussian elimination without pivoting in O(n); the matrix is strictly diagonally dominant (diagonal exceeds the sum of the off-diagonals by 1 + θβΔt), so no pivot can vanish and the algorithm is backward stable.

### 2.3 Exact solutions of the discrete equations

Before any convergence study, test things that must hold *exactly* (`@langtangen-fd-computing-exponential-decay` 3.1.4, `@langtangen-linge-fd-computing-pdes` 2.2.4, 1.2.2). A **constant** u = c with q = 0 and both ends at c satisfies (1) identically: D₂c = 0, and the time difference is zero. A solver that does not return exactly c (to rounding) has a wrong boundary row or a sign error, and no order study is needed to find it. Stronger: u = 2t x(L − x) with source q = 2x(L − x) + 4αt. The central difference of a quadratic is exact (u_xxxx = 0 kills the Δx² term in (2)), the Crank–Nicolson average of a quantity linear in t is exact (u_ttt = 0 and q_tt = 0 kill the Δt² terms), so this polynomial is an **exact solution of the discrete equations** on any grid and any step. The code reproduces it to 7 × 10⁻¹⁵ K after ten steps on 40 cells: that is the rounding error of a few hundred floating-point operations, and the test demands 10⁻¹¹. The classic **separable solution** u = T₀ sin(πx/L) e^{−α(π/L)²t} of the homogeneous problem is the "analytical solution of physical significance" of `@langtangen-linge-fd-computing-pdes` 2.2.2: with T₀ = 50 K the L2 errors on 25, 50, 100, 200 cells (Δt = 300 s/nx) are 1.04 × 10⁻², 2.59 × 10⁻³, 6.47 × 10⁻⁴, 1.62 × 10⁻⁴ K, orders 2.0007, 2.0002, 2.0000.

### 2.4 Manufactured solutions and the observed order

Analytical solutions exist only for simple cases (no source, no loss, separable data), which is exactly where bugs do not hide. The **method of manufactured solutions** reverses the problem: *choose* any smooth u_m(x, t), compute the source q_m = ∂_t u_m − α ∂_xx u_m + βu_m that makes it a solution, take the initial and boundary data from u_m itself, run the solver with q_m and compare with u_m. The function is arbitrary, so pick one that exercises everything: time dependence that is not linear (so Δt² terms exist), space dependence with u_xxxx ≠ 0, nonzero values wherever a sign could be wrong. The lesson's choice,

u_m = 40 sin(πx/L)(1 − e^{−t/τ}) + 10 sin(2πx/L) e^{−t/τ},   τ = 200 s,   (3)

has q_m = (40/τ) sin(πx/L) e^{−t/τ} + 40α(π/L)² sin(πx/L)(1 − e^{−t/τ}) − (10/τ) sin(2πx/L) e^{−t/τ} + 10α(2π/L)² sin(2πx/L) e^{−t/τ}; `manufactured_source` lets SymPy differentiate so that the learner's hand algebra is not the weakest link (the test checks SymPy's output against a hand formula on a simpler case). Note that q_m has no physical meaning; a heater that produces (3) does not exist, and that does not matter: verification is about the equations, not the physics.

With Δt = 300 s/nx the discrete L2 errors √(Δx Σ(u − u_m)²) are

| nx | 25 | 50 | 100 | 200 | 400 |
|---|---|---|---|---|---|
| error [K] | 1.480 × 10⁻² | 3.696 × 10⁻³ | 9.238 × 10⁻⁴ | 2.309 × 10⁻⁴ | 5.773 × 10⁻⁵ |
| observed order | | 2.002 | 2.000 | 2.000 | 2.000 |

where the **observed order** between two grids refined by r is p = ln(e_coarse/e_fine)/ln r (`@langtangen-fd-computing-exponential-decay` 3.1.6, "Estimating r"). The sequence of p's converging to the formal order 2 from above is the signature of a correct code in its asymptotic range: the error is C Δx² + higher-order terms whose share shrinks. Backward Euler on the same problem gives errors 0.23, 0.12, 0.06, 0.03, 0.015 K and orders 0.96, 0.98, 0.99, 0.99: the Δt term of (2) dominates and the order is one, as predicted.

**Order in time without an exact solution.** Fix a fine grid (400 cells) and halve Δt: compared against u_m the errors are 1.51 × 10⁻², 3.79 × 10⁻³, 9.76 × 10⁻⁴, 2.74 × 10⁻⁴ K for 10, 20, 40, 80 steps and the orders 1.99, 1.96, 1.84 *fall*, because the spatial error (5.8 × 10⁻⁵ K) is becoming a floor. The remedy is to compare the solutions with each other rather than with the exact one: the point value u(0.15 m, 300 s) is 27.2847, 27.2679, 27.2637, 27.2626 K, and p = ln((f₃ − f₂)/(f₂ − f₁))/ln 2 from each triplet is 2.002 and 2.0005: the floor cancels in the differences. That is the Richardson idea of §2.6, used for verification; it needs no exact solution at all, which is why it works on the real problem.

### 2.5 Planted bugs: does the test catch what it is for?

A verification test is only as good as the bugs it can catch, so plant some. `heat_theta(..., bug="source_time")` evaluates the source at t_n instead of the θ-weighted level. By (2) this adds (Δt/2) q_t to the truncation error: the scheme still converges, but at first order. Observed: errors 0.080, 0.040, 0.020, 0.010, 0.005 K and orders 1.14, 1.08, 1.04, 1.02. The solution at 400 cells is still only 0.005 K wrong, which a plot would never show, and a comparison with the exact solution at a single resolution would call "accurate"; the *order* test exposes it at once. `bug="diffusivity"` uses 1.02α: the code converges perfectly, to the solution of the wrong equation. Errors 0.14, 0.15, 0.15, 0.15, 0.15 K, observed order ≈ 0: an **error plateau**, the signature of a converged solution of the wrong problem (a wrong constant, a wrong sign in a term that happens to be small, a boundary condition applied to the wrong node). Both bugs would pass the constant-solution test; only the first would pass a plot; neither passes the manufactured-solution order test. This is the content of "testing" in `@langtangen-linge-fd-computing-pdes` 2.2.3: the test oracle is the *rate*, not the error.

**Backward error of the solve** (`@ocw-18-335j` Lecture 3). For the linear-algebra piece the right oracle is not "does x agree with SciPy to 10⁻¹²" but "is x the exact solution of a nearby problem": the normwise relative backward error ‖Ax − b‖/(‖A‖‖x‖ + ‖b‖). A backward-stable algorithm returns a few machine epsilons whatever the conditioning; the *forward* error may still be as large as κ(A) times that, and that is the problem's fault, not the algorithm's. For the θ-method matrices (κ ≈ 1 + 4θr ≈ 50 at r = 12) the Thomas solver returns a backward error of 3.7 × 10⁻¹⁷; on a deliberately ill-conditioned tridiagonal (diagonal 2 − 10⁻⁶, κ = 1.6 × 10⁴) still 1.0 × 10⁻¹⁶, and the forward difference from a dense LU is 6.5 × 10⁻¹⁶: the algorithm is doing its job and the conditioning is benign here.

### 2.6 Solution verification: Richardson extrapolation and the GCI

The heater problem (Gaussian strip, q = Q e^{−(x−x₀)²/2w²}, Q = 0.5 K/s, w = 30 mm, x₀ = 0.2 m) has no closed-form solution. How far is the 100-cell answer from the converged one? Write the error expansion for a functional f (a temperature at a point, a heat flux, a maximum): on grid spacing h in the asymptotic range,

**f_h = f_exact + C hᵖ + higher-order terms.**   (4)

Three grids with constant refinement ratio r (h, rh, r²h: fine f₁, medium f₂, coarse f₃) give three equations for f_exact, C and p. Subtracting pairs eliminates f_exact: f₂ − f₁ = C hᵖ(rᵖ − 1), f₃ − f₂ = C hᵖ rᵖ(rᵖ − 1), so

**p = ln((f₃ − f₂)/(f₂ − f₁))/ln r,   f_exact ≈ f₁ + (f₁ − f₂)/(rᵖ − 1)**   (5)

(the second is **Richardson extrapolation**; `@nasa-nparc-cfd-vv-tutorial` "Order of Grid Convergence" and "Richardson Extrapolation"). The **grid convergence index** turns the fine-grid change into an error band: GCI_fine = F_s |ε₂₁|/(rᵖ − 1) with ε₂₁ = (f₂ − f₁)/f₁ and a safety factor F_s = 1.25 when three grids are available (3 with two): it is the Richardson error estimate with 25 % margin, and reads "the fine-grid value is within GCI (relative) of the converged value, with the confidence that experience with many codes has earned the factor 1.25" ("Grid Convergence Index (GCI)"). Two further tools follow from (4): the grids are in the **asymptotic range** if GCI₃₂/(rᵖ GCI₂₁) ≈ 1 ("Asymptotic Range of Convergence"), and the refinement needed to bring the GCI to a target is (GCI/target)^{1/p} ("Required Grid Resolution"). One caution that the formulas hide: if p is *computed* from the same three values, the asymptotic ratio equals f₁/f₂ by construction and tests nothing; the check has teeth only when p is the scheme's formal order, which `richardson(..., p_formal=2.0)` allows. With four grids one can compute p from two triplets instead.

For the temperature rise at the heater centre, x = 0.2 m (a node of every grid used), after 600 s:

| nx | 25 | 50 | 100 | 800 (reference) |
|---|---|---|---|---|
| f [K] | 38.3781 | 38.2531 | 38.2226 | 38.2126 |

Observed p = 2.034, Richardson f_exact ≈ 38.2127 K (the 800-cell reference is 38.2126 and its own extrapolation 38.21245), GCI_fine = 0.0323 %, actual |f₁ − f_ref|/f₁ = 0.0261 % (inside the GCI, as the factor 1.25 intends), asymptotic ratio with p = 2 equal to 1.023. To bring the GCI to 0.01 % the fine grid must be refined by (0.0323/0.01)^{1/2.03} = 1.78. In absolute terms the numerical uncertainty of the 100-cell model is **u_num = 0.0323 % × 38.2 K = 0.012 K**, forty times smaller than the thermocouple uncertainty: numerics will not be what limits the validation.

**A functional that is not in the asymptotic range.** Take instead the *maximum over the nodes* at t = 600 s: 38.3781, 38.3188, 38.3178 K on 25, 50, 100 cells. The formulas return p = 5.93 and an asymptotic ratio with p = 2 of 15.3; the next triplet (50, 100, 200) has differences of opposite sign and `richardson` raises. The functional is not a smooth function of the grid: the node under the peak moves as the grid changes, which adds an O(Δx) wobble that is not of the form (4). The lesson: Richardson applies to quantities that converge smoothly (point values at common nodes, integrals), and a p far from the formal order is a warning, not a result (`@nasa-nparc-cfd-vv-tutorial` "Example Grid Convergence Study" discusses the same symptom).

### 2.7 Validation: comparison error and its uncertainty

Validation compares the model with measurements of the real system. The data in this lesson are **synthetic**, generated by `synthetic_measurements`: the same solver with the true convective loss β_true = hP/(ρcA) = 8.2 × 10⁻⁴ s⁻¹ (h = 5 W/m²K on a 10 mm square section), on a fine grid, sampled at four thermocouples (x = 0.1, 0.2, 0.3, 0.4 m) at six times (100 to 600 s), plus Gaussian noise of standard deviation σ = 0.3 K (seed 18; the realised noise has an RMS of 0.307 K). The model under test has β = 0: the designer forgot that the rail loses heat to the air. The procedure would be identical with real data.

Define the **comparison error** E = model − data at each point and the **validation uncertainty** u_val = √(u_data² + u_num²), here √(0.3² + 0.012²) = 0.300 K. A model is validated *at the level u_val* if |E| is consistent with u_val: a reduced chi-square Σ(E/u_val)²/N near 1, almost all |E| < 2u_val. The lossless model gives

| t [s] | E at 0.1 m | 0.2 m | 0.3 m | 0.4 m |
|---|---|---|---|---|
| 100 | 0.45 | 0.88 | 0.14 | 0.44 |
| 300 | 1.06 | 1.57 | 2.34 | 0.77 |
| 600 | 2.90 | 4.60 | 4.46 | 2.38 |

(in K): 5 of 24 points within 2u_val, reduced χ² = 61, E/u_val up to 15, and a *pattern*: the error is positive everywhere, grows with time and is largest where the temperature is highest. That is not noise (noise has no pattern) and not numerics (u_num = 0.012 K); it is **model-form error**, and its shape says what is missing: a loss proportional to temperature. A hand estimate of the missing term, βu·t ≈ 8 × 10⁻⁴ × 35 K × 600 s ≈ 17 K if nothing else happened, bounded by conduction to about a quarter of that, matches the 4.6 K seen.

**Calibration is not validation.** `fit_loss_coefficient` minimises χ² over β: β̂ = 7.92 × 10⁻⁴ s⁻¹ in ten model runs, with a standard uncertainty of 0.23 × 10⁻⁴ from the curvature of χ² (the true 8.20 is 1.2σ away), reduced χ² = 0.98, 23 of 24 points within 2u_val. The calibrated model now "agrees with the data"; it also agreed before anybody knew the physics, because one free parameter can absorb one pattern. Whether β̂ = 7.9 × 10⁻⁴ s⁻¹ (equivalent h = 4.8 W/m²K) is a *physical* loss coefficient or a fudge that also hides a heater-power error, a contact resistance at the sinks or a thermocouple bias can only be learned from data not used in the fit (a different heater power, a longer time, a fifth sensor), which is why NASA-STD-7009 asks for validation on the *intended use* and not on the fitting set. Problem 5 does the hold-out test.

### 2.8 Where the model stops being valid

- **One-dimensional.** The Biot number hw/k ≈ 5 × 0.01/237 = 2 × 10⁻⁴ justifies it here; a 100 mm block would not be.
- **Linear.** Aluminium's k and c change by about 10 % between 20 and 200 °C; a 40 K rise is at the edge.
- **Ideal sinks.** A contact resistance at the clamps raises the end temperature; its signature in E would be an offset that grows toward the ends, distinguishable from the loss term's shape, if the sensors resolve it.
- **The synthetic data.** They contain exactly one unmodelled effect and Gaussian noise. Real thermocouples have bias, time lag and position error, and the real bar has all of the above at once. The procedure is the same; the diagnosis is harder.

### Step 1: the linear solver and its backward error

```python
def thomas_solve(lower, diag, upper, rhs):
    n = diag.size
    c, d = diag.astype(float).copy(), rhs.astype(float).copy()
    for i in range(1, n):                       # forward elimination
        m = lower[i] / c[i - 1]
        c[i] -= m * upper[i - 1]
        d[i] -= m * d[i - 1]
    x = np.empty(n)
    x[-1] = d[-1] / c[-1]
    for i in range(n - 2, -1, -1):              # back substitution
        x[i] = (d[i] - upper[i] * x[i + 1]) / c[i]
    return x
```

Raise `ValueError` on a zero pivot. `backward_error` uses the given `tridiagonal_matvec` for the residual and the maximum row sum for ‖A‖_∞.

### Step 2: the θ-method

Build the three constant diagonals once (diagonal 1 + θ(2r + βΔt), off-diagonals −θr), then per step: the explicit part u + (1 − θ)Δt(αD₂u − βu), plus Δt times the θ-weighted source, plus θr times the new boundary values in the first and last rows; solve; write the boundary values into the new level. Implement the two `bug` flags exactly as documented in the docstring (the tests plant them) and raise on an unknown flag. Return the full history `(nt + 1, nx + 1)`.

### Compare

`scipy.linalg.solve_banded` is the production tridiagonal solver (LAPACK `gtsv`, with pivoting, which Thomas lacks and which matters for matrices that are not diagonally dominant); `scipy.sparse.linalg` and `scipy.integrate.solve_ivp` with the method-of-lines would solve the same PDE; and the structure of the verification (exact solutions, manufactured solutions, rate tests as `pytest` oracles) is the one `@langtangen-fd-computing-exponential-decay` 3.1.6 recommends ("Why convergence rates are important"): a rate test is an *absolute* criterion, while "the error is small" is relative to an unstated expectation. What writing it bought is the habit of treating every claim about a simulation as a requirement with a method of verification, and the knowledge that "the code agrees with the experiment" can mean the code is right, or that one parameter was tuned until it did.

- **What if a reviewer swaps α for 1.02α in the released code?** The manufactured-solution test fails with an error plateau at 0.15 K; the separable-solution order test *also* fails (plateau); the constant-solution and polynomial tests pass (the polynomial has u_xxxx = 0 but its source contains 4αt, so check: it fails too, because q was built with the true α).
